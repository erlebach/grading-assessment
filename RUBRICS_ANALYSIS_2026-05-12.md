# Rubrics Directory — Analysis as of 2026-05-12

## Overview: Three Distinct Rubric Locations

The repo has three separate rubric locations with different roles and origins:

| Location | Status | Origin | Used by |
|----------|--------|--------|---------|
| `rubrics/q0N.yaml` (root flat files) | **Placeholder stubs** — generic CS101 content, not data-mining questions | Unknown scaffold/template | Not used by any active pipeline |
| `rubrics/yaml/q0N.yaml` | **Authoritative LLM-generated rubrics** for the data-mining course | `create_dynamic_rubrics_for_each_question.py --rubrics-dir rubrics` | v1 grading pipeline |
| `rubrics_dynamic/yaml/q0N.yaml` | **Working/experimental LLM-generated rubrics** | Same script with default `--rubrics-dir rubrics_dynamic` | v1 dynamic pipeline |

---

## What `rubrics/q01.yaml` Is (Root Flat Files)

**Placeholder stubs.** These files (`q01.yaml`–`q10.yaml`) contain generic CS101 content
("Implement a function to calculate factorial", "Implement a function to reverse a string")
that has nothing to do with the actual data-mining course. They appear to be scaffolding
left over from an early setup phase, not generated by any pipeline and not used by any
active code.

```yaml
# rubrics/q01.yaml — STUB, not authoritative
question_id: "q01"
question_text: "Implement a function to calculate factorial"   ← wrong course entirely
total_points: 10
criteria:
  - criterion_id: "correctness"
    ...
```

---

## What `rubrics/yaml/q01.yaml` Is (Authoritative Rubrics)

**LLM-generated, reviewed, and promoted to authoritative status.** These are the real
data-mining rubrics. They have the correct question text (objects/attributes in data
tables, zip code example, etc.) and detailed full-credit criteria descriptions.

```yaml
# rubrics/yaml/q01.yaml — AUTHORITATIVE
question_id: q01
question_text: "In the context of a data table, precisely distinguish an 'object' ..."
total_points: 10
scoring_weights:
  definition_accuracy:       { keyword: 0.5, semantic: 0.5 }
  alternative_names_completeness: { keyword: 0.5, semantic: 0.5 }
  distinction_clarity:       { keyword: 0.5, semantic: 0.5 }
  contextual_understanding:  { keyword: 0.5, semantic: 0.5 }
semantic_decay: linear
semantic_top_k: 5
criteria:
  - criterion_id: definition_accuracy
    description: "Full credit is earned when the answer correctly defines an object
      as a data instance that has a collection of attributes..."
    points: 3
    evidence_required: true
    evaluation_method: semantic
  ...
metadata:
  generated_by: llm
```

The key feature: each `description` is a **full-credit benchmark statement** — a
prose specification of what a perfect answer looks like for that criterion. This is
what the user refers to as "the reasoning of the LLM to justify the score."

## What Generates `rubrics/yaml/` and `rubrics/json/`

**Single script:** `grading_pipeline/create_dynamic_rubrics_for_each_question.py`

### Run command

```bash
python -m grading_pipeline.create_dynamic_rubrics_for_each_question \
    --source-file grading_pipeline/sources/slides_data_type_quality.pdf \
    --questions-file ten_questions.md \
    --rubrics-dir rubrics          # ← puts output in rubrics/ (authoritative location)
                                   # default is rubrics_dynamic/
```

### Internal flow

```
ten_questions.md + source PDF
│
├─ load_prompt_template()         read rubric_generator_template.txt
├─ format_prompt()                inject question text + source material
├─ generate_rubric_with_llm()     LLM call → validates with RubricJsonResponse schema
│   └─ Pydantic validation:
│       - 3–6 dimensions (criteria)
│       - points per dim in {1,2,3,4}
│       - total_points == 10
│       - all descriptions non-empty
│
└─ save_rubric_dual_format()      writes 4 files per question:
    ├─ rubrics/json/q0N_raw.json                         ← raw LLM output
    ├─ rubrics/json/q0N_converted.json                   ← full rubric structure
    ├─ rubrics/json/q0N_title_description_converted.json ← criterion titles + descriptions only
    └─ rubrics/yaml/q0N.yaml                             ← pipeline-ready YAML
```

### The three JSON artifacts explained

**`_raw.json`** — The LLM's direct output. Contains `dimensions` (not `criteria`) with
human-readable `title` and `description` fields before slugification:

```json
{
  "dimensions": [
    {
      "title": "Understanding the Attribute-Property Principle",
      "points": 4,
      "description": "A full-credit answer explicitly explains that the permissible
        analyses are dictated by an attribute's intrinsic properties (nominal, ordinal,
        interval, ratio) rather than the syntactic data type of its values..."
    }
  ],
  "total_points": 10
}
```

This is the "LLM reasoning" the user referred to — each dimension description is the
LLM's specification of what constitutes a correct answer.

**`_converted.json`** — The `_raw.json` converted to grading-pipeline format:
- `title` slugified → `criterion_id` (e.g. "Understanding the Attribute..." → `understanding_the_attributeproperty_principle`)
- `scoring_weights` block added (default 50/50 keyword/semantic)
- `evidence_required: true`, `evaluation_method: semantic` added per criterion
- `metadata` block added

**`_title_description_converted.json`** — Subset for downstream processing (only
`criterion_id`, `title`, `description` per criterion; used by `criterion_loader.py`).

## Addendum (2026-05-12, second pass) — New findings

### 1. There are TWO rubric-generation scripts, not one

| Script | Mechanism | Default output | What it writes |
|--------|-----------|----------------|----------------|
| `grading_pipeline/create_dynamic_rubrics_for_each_question.py` | **LLM** (prompt + retry + overlap check) | `--rubrics-dir rubrics_dynamic` (default), or `rubrics` if passed | Four files per question under `<dir>/json/` and `<dir>/yaml/` |
| `grading_pipeline/create_rubrics_for_all_questions.py` | **Non-LLM**, hard-coded template | `--rubrics-dir rubrics` (default), `--start-from 3` | A single flat `<dir>/q0N.yaml` per question; 2 generic criteria (`correctness`, `completeness`) |

The second script is what produced the root `rubrics/q03.yaml`–`rubrics/q10.yaml` stubs (timestamps Jan 17, 2-criterion, course `Data Mining`, real question text from `ten_questions.md`).

### 2. Root stubs are heterogeneous — not all from the same source

- `rubrics/q01.yaml`, `rubrics/q02.yaml` (May 11 timestamp, `@` extended attrs): CS101 content (`factorial`, `reverse a string`), 3 criteria (`correctness`, `edge_cases`, `style`). Match **neither** generator's template — pre-data-mining hand-edited scaffolding.
- `rubrics/q03.yaml`–`rubrics/q10.yaml` (Jan 17 timestamp): `Data Mining` course, 2 criteria, real data-mining question text. Match the `create_generic_rubric()` template in `create_rubrics_for_all_questions.py` exactly.

### 3. Root flat files ARE actively referenced (correction to prior section)

`grading_pipeline/config/rubrics.yaml` maps:

- `q01` → `../../rubrics/q01.yaml`        ← root stub (CS101!)
- `q02` → `../../rubrics/q02.yaml`        ← root stub (CS101!)
- `q03` → `../../rubrics/q03.yaml`        ← root stub (2-criterion generic)
- `q04`–`q10` → absolute paths under `rubrics_dynamic/yaml/q0N.yaml`

This config is read by `grading_pipeline/config_loader.py::get_rubric_path()`, which is called from `grading_pipeline/cli.py:111` and `cli.py:198`. So v1 CLI invocations for q01 or q02 would load the CS101 stubs as the actual rubric — a latent bug.

### 4. The LLM generator does not overwrite existing config entries

`create_dynamic_rubrics_for_each_question.py:765` guards the config write with `if question_id not in config["rubrics"]`. Once `q01` has an entry pointing to the root stub, re-running the script never updates it — even if the script just wrote a fresh `rubrics/yaml/q01.yaml`. The `rubrics/yaml/q0N.yaml` files exist (Jan 21 timestamps) but the config still points at the older root stubs for those same IDs.

### 5. Two rubric configs coexist

| Config | Used by | Maps to |
|--------|---------|---------|
| `grading_pipeline/config/rubrics.yaml` | `grading_pipeline/cli.py` (v1 main CLI) | Root + rubrics_dynamic mix (see above) |
| `grading_dynamic_rubrics/config/rubrics.yaml` | `grading_dynamic_rubrics/cli.py` | All 10 → `../../rubrics_dynamic/yaml/q0N.yaml` |

`rubrics_dynamic/yaml/` currently only contains q01–q05 — the q06–q10 paths in both configs point to non-existent files.

### 6. Where the LLM "reasoning" actually lives

The user's intuition that "the LLM reasoning justifying the score" is in a flat `q0N.yaml` was reversed: it lives in `rubrics/yaml/q0N.yaml` (and equivalently in `rubrics/json/q0N_raw.json`). The root `rubrics/q0N.yaml` files contain **no LLM-generated content**:

- q01/q02 root: hand-edited CS101 stubs
- q03–q10 root: generic 2-criterion template emitted by a non-LLM script

The richest representation of the LLM justification is `rubrics/json/q0N_raw.json` — full paragraph descriptions per dimension with `title` preserved (not yet slugified into `criterion_id`).

### 7. Prompt template structure (for context)

`grading_pipeline/rubric_generator_template.txt` asks the LLM for:
- 2–5 dimensions, points summing to exactly 10
- Each dimension categorized as `semantic` / `application` / `clarity`
- Each dimension to contain 1–4 atomic, binary, positively-phrased checks with float weights

The per-check structure is **discarded** when converting to YAML — only the dimension-level `description` survives in `rubrics/yaml/q0N.yaml`. The `_raw.json` also lacks per-check fields (it only contains `dimensions[*].title/points/description`), so the template asks for richer output than the schema captures.

### 8. v2 does not touch any `rubrics/` path

`v2/rubric_generator.py` has no `rubrics_dir` reference and no disk persistence. v2 regenerates rubrics in-memory each run, consistent with the v2 section below.

## What v2 Replaced (and What It Lost)

v1 used `rubrics/yaml/q0N.yaml` directly — one hand-promoted rubric per question with
keyword/semantic scoring weights. v2 discarded this in favour of generating concept-check
rubrics at runtime via `RubricGeneratorV2`.

What was lost:
- **The `_raw.json` full-credit prose** — the LLM's natural-language justification of
  what a correct answer looks like. v2 has `ConceptCheck.precision_levels` (full/partial/none
  descriptions) but these are terse; the v1 raw descriptions were paragraph-length and
  much richer.
- **Pre-generated, stable rubrics** — v1 rubrics were fixed files you could inspect and
  edit; v2 regenerates them every run (no caching yet).
- **Criterion descriptions as score justification** — in v1 grade output the criterion
  `description` appeared alongside the score, explaining what the criterion tested. v2
  currently only saves the final float score and convergence status.
